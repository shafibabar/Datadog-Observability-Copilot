  • The knowledge that closes that gap lives in a handful of experienced engineers' heads.

How the work was structured

I approve and direct. The AI executes.

I don't write or debug the code. What I do is decide what gets built, in what order, and whether the result is acceptable.

GateWhat had to happen before any code
PlanAgree the problem, the slice, and what we were explicitly not building
DesignAgree the architecture and its seams — where future change would land
RoadmapAgree iteration by iteration, with deferrals named out loud
ApproveAn explicit yes from me. Then, and only then, implementation

No dependency, architecture change, or cost was ever added silently — each came to me as a recommendation with alternatives and a default.

Where human judgment was still required

The four times I had to overrule it

  • “Why is it giving scripted answers?” — it was reasoning beautifully over demo data and had no idea which dashboard, environment or tenant to look at. A real architectural gap.
  • “The UI is completely screwed up.” — twice. Correct code, broken experience. Only I was looking at the actual screen.
  • “Only these ~500 metrics are in scope, and I won't fill in the rest.” — scope and effort budget are mine to set, not its.
  • “I cannot do the demo with replay.” — it offered a safe fallback. Refusing it is the only reason the live integration works today.

Failure story 1

The UI that broke twice, for the same reason

  • Panels stacked and shoved sideways. Tabs that silently didn't switch.
  • Both times the code was correct — the browser was running a cached stylesheet and cached script from a previous version.
  • Tests passed throughout. They asserted the markup existed, never that it worked.

The fix was structural, not cosmetic: the layout was rebuilt to render with zero JavaScript, tab switching became pure CSS, and every asset URL now carries its modification time so a stale cache is impossible. Lesson recorded in the repo: don't mark UI behaviour “manual-smoke-only” — make it declarative and testable.

Failure story 2

360 green tests missed four real defects

The moment it touched the real Datadog org, four things broke that no mock could have caught:

DefectWhy no test found it
Wrong tag nameOur org has no env tag at all. A wrong tag returns HTTP 200 and zero rows — it fails silently
Sparse metricsThese metrics emit ~40–150 points per week. Every 4-hour query looked like an outage
420 queries per questionA safeguard keyed off the wrong source, so it silently stopped bounding anything
1,000-row timelineThe real event API returns ~1,000/hour. The test fixture had five

Tests prove the code does what you think. Only real data proves that what you think is true.

Why I could trust work I can't read

Test-first, and once green always green

  • Specs were written before the implementation, so they describe intent rather than echo the code.
  • Every step ran the whole suite. A previously passing test failing was treated as a stop-work event.
  • Coverage held at 98% throughout — and I have a per-step log of every change.

What this is and isn't

An honest scope statement

Real and working

  • Live read-only Datadog integration
  • Genuine reasoning — no hard-coded answers
  • Persisted, versioned investigation state
  • 5 personas · evidence tracing · 1 artifact
  • 388 tests, 98% coverage

Deliberately not built

  • 5 of 6 output artifact types
  • Logs and traces (metrics + events only)
  • Ticketing / paging integrations
  • Any multi-user or auth story
  • One UI flow still unverified in a real browser

A coherent slice with clean seams — not a shippable product. Every omission above was a decision, and it's written down.

If you want to try this

Six things that made it work

  • Make it plan before it builds. A third of my prompts were planning. That ratio is the difference between direction and drift.
  • Demand tests you don't have to read. They are how you approve work you cannot personally audit.
  • Force the decisions into files. Chat is disposable; the repo is not.
  • Point it at reality early. Everything expensive I found came from real data, not from mocks.
  • Say no. Refusing the convenient fallback is where most of the real value came from.
  • Ask it to prove claims, not assert them. “Show me it working” beats “is it done?”
