Internal showcase

Observability Copilot

A reasoning layer over our telemetry that turns a dashboard into a guided, evidence-backed investigation — running live against our own Datadog org.

Not a chatbot. Not a dashboard replacement. The dashboard stays the source of truth; this explains what it means.

The problem

The data is all there. The understanding isn't.

  • Open a dashboard for a service you don't own. Dozens of panels, every one technically correct.
  • You can't tell what's normal, what changed, or what matters right now.
  • So you find someone who's seen it before. That person is the bottleneck — and they're asleep.

The gap isn't data collection. It's interpretation — and it currently lives in a handful of heads.

The design constraints

Four rules it must never break

  • Explain metrics, don't expose them. Answer the question, don't render another graph.
  • Tell the story. An ordered narrative of what happened, not a wall of panels.
  • Every conclusion carries its evidence. “Show me why” is always available.
  • Facts, hypotheses, recommendations and unknowns stay separate. Confidence must trace to evidence — never speculation dressed as certainty.

How it works

Four layers, each replaceable

LayerJob
TelemetryOne interface over metrics and events. Live Datadog, or a replayable scripted incident — swapping backends changes nothing above
ReasoningProduces structured objects: a claim, its category, a confidence, and pointers to evidence. Cited evidence is validated, so it cannot invent support
WorkspaceThe centre of gravity. A persisted, versioned investigation — a living document, not derived from chat
PresentationDashboard and copilot side by side. Headline → summary → evidence → raw telemetry, on demand

Personas, workspace sections and artifact types are all registry-driven — adding one is config, not surgery.

Why the answers are grounded

What happens between your question and the answer

1 · GuardOff-topic or prompt-injection input is refused before any expensive work — zero tokens spent
2 · ScopeWhich environments, which tenants, what time window. Persisted per conversation, changeable per question
3 · Resolve420 metrics in scope → the 8 most relevant to this question. Deterministic, so it's explainable and repeatable
4 · EvidenceQuery only those. Build a catalog of citable facts with real values
5 · ReasonThe model must cite catalog IDs. Invented citations are stripped out

Deliberately not built

Where it went wrong

Two failures worth showing you

  • The UI broke twice, identically. Both times the code was correct — the browser was running a cached stylesheet. Tests checked that the markup existed, never that it worked. Fixed structurally: the layout now renders with zero JavaScript.
  • 360 green tests missed four real defects. The first contact with the real org found a tag that doesn't exist in our org, metrics that emit 40–150 points a week, a safeguard that had silently stopped bounding queries, and a 1,000-row timeline.

Tests prove the code does what you think. Only real data proves that what you think is true.

Why I could trust work I can't read

Test-first, once green always green

  • Specs written before implementation, so they capture intent, not the code.
  • A previously passing test failing was a stop-work event. Coverage held at 98%.
  • 23 decisions and 20 build-log entries in version control — the repo remembers, so the chat doesn't have to.

What actually made it work

  • Make it plan before it builds — a third of my prompts, and the reason it stayed on course.
  • Demand tests you don't have to read — that's how you approve what you can't audit.
  • Force decisions into version-controlled files — chat is disposable.
  • Point it at reality early — mocks only confirm what you already believe.
  • Say no to the convenient shortcut — that's where most of the value came from.

The bottleneck moved from writing software to deciding what to build.
