## Commands

All commands assume the venv is active: `source .venv/bin/activate` (prompt shows `(.venv)`). First-time setup and the full run/demo walkthrough live in `README.md`.

```bash
# Install (app only / app+test)
pip install -r requirements.txt
pip install -r requirements-dev.txt

# Run the product app → http://127.0.0.1:8000  (needs ANTHROPIC_API_KEY in .env; degrades gracefully without)
python -m uvicorn app.main:app --port 8000

# Run the metrics dashboard → http://127.0.0.1:8055  (stdlib collector; no key needed)
python -m uvicorn metrics.dashboard:app --port 8055

# Tests (LLM is faked — no API key, no network, no spend)
pytest                                                  # full suite
pytest -q                                               # quiet
pytest tests/test_config.py::test_defaults_when_unset   # a single test
pytest --cov=app                                        # with coverage
```

Tests are marked `@pytest.mark.pending` when written red-ahead-of-implementation (TDD). The regression invariant is binding: **once green, always green** — every step runs the full suite before proceeding. See `docs/context/TESTING.md`.

**A pre-commit hook enforces the TDD log:** staging anything under `tests/` without staging `docs/context/TESTING.md` fails the commit. Logic in `scripts/check_testing_log.py` (stdlib-only so it runs with no venv), hook in the committed `.githooks/` (because `.git/hooks/` isn't version-controlled), specs in `tests/test_hooks.py`. Enable once per clone with `git config core.hooksPath .githooks`; bypass a genuine exception with `git commit --no-verify`.

## Code layout

Four deliberately separable layers (a real backend, more personas/artifacts, and downstream integrations must slot in without rewrites):

- **`app/telemetry/`** — `DataSource` interface (`base.py`) over normalized timestamped events. `ReplayAdapter` (`replay.py`) scripts the canonical deployment-induced latency incident for a reliable demo; `LiveDatadogAdapter` (`datadog.py`) is a read-only Datadog REST adapter. Selected by `COPILOT_DATA_SOURCE` (`replay` default / `datadog`). **Metric scope** is one allowlist: `DATADOG_METRIC_NAMESPACES` (e.g. `ec.*, ea.*`) parsed by `namespaces.py` (pure, stdlib `fnmatch`) and applied to every source of metrics — `discover_metric_names()` (live via `GET /api/v1/metrics`, **confirmed working**: 16,117 names / 1,297 `ec.*` on the real org; best-effort, any failure → `[]`), the Terraform extraction, and the registry merge. Blank = no filtering; the built-in registry (below) is now the zero-config baseline for the Datadog source, so the illustrative `system.*` defaults only apply at the adapter seam (`metric_queries=None`). `filter_queries` also drops Datadog's generated statistical sub-metrics (`is_stat_submetric`: `.count/.sum/.min/.max/.avg/.median/.NNpercentile` — one distribution yields ~5 names; 1,297 ≈ 500 distinct signals). The retired `DATADOG_DISCOVERY_METRIC` is gone: tag-value enumeration now groups an in-scope metric from the registry.
- **`app/reasoning/`** — `ReasoningEngine.investigate(question, history=...)` (`engine.py`) calls Claude behind the `LLMClient` seam (`llm.py`, faked in tests) and assembles a structured `Investigation` of reasoning objects (claim · category fact/hypothesis/recommendation/unknown · confidence · evidence pointers), an ordered `timeline.py`, and an `evidence.py` catalog. `domain.py` holds a **static EC domain knowledge base** (services, metric categories, failure modes) baked into `_SYSTEM` at import time. Two real LLM backends implement the seam: `ClaudeCliClient` (shells out to the local `claude` CLI — **no API key**, the "Claude Code way") and `AnthropicClient` (Anthropic SDK, needs a key). `build_copilot` picks one via `COPILOT_LLM_BACKEND` (`auto`/`cli`/`sdk`; `auto` = CLI when no key, else SDK). Conclusions are grounded in evidence; invalid evidence pointers are filtered.
- **`app/workspace/`** — the Investigation Workspace: SQLite **append-with-history** store (`store.py`, versioned snapshots + `messages`/`conversations` tables) and a registry-driven `sections.py` (`serialize_sections()` → JSON for the live panel). This is the architectural center of gravity — a living document, not chat-derived.
- **`app/` presentation & orchestration** — `main.py` (FastAPI: `/api/conversations[/{id}[/chat|/artifact]]`, `/api/status`, `/healthz`), `copilot.py` (`Copilot` conversation-aware service joining the three layers; factory `build_copilot(settings)`), `personas.py` (registry of 5 personas; `render()` re-frames the **same facts** deterministically with **no LLM call**), `artifacts.py` (registry of `ArtifactSpec` transforms over the Investigation, `to_markdown()`; Incident Summary built), `config.py` (secret loading — secrets never touch git or the DB), `web/` (static UI). A pre-reasoning **relevance & abuse guard** (`guard.py`, `evaluate()` → `GuardVerdict`) gates the expensive reasoning path: Stage 1 is deterministic/zero-token (block empty/over-long/injection, fast-allow on a broad keyword list that includes EC service names and queue/processing vocabulary); Stage 2 (hybrid mode) consults an LLM classifier for the ambiguous middle. The Stage-2 classifier **is wired** (`guard_classifier.py` → `classify_relevance`, hooked up in `build_copilot`) and deliberately lets errors propagate so `guard.py`'s fail-*closed* contract governs (a raising classifier counts as "refuse"). Wired into `Copilot.ask` before anything is persisted; `_SYSTEM` is hardened to treat inputs as untrusted. Config: `COPILOT_GUARD_ENABLED/MODE/MAX_CHARS`.
- **`app/monitors/`** — the **correlation layer** over a local checkout of the Terraform repo `ec-conduct-dd-monitors`, located via **`MONITORS_REPO_PATH`** (machine-specific; empty/missing → empty index, graceful). `index.py` extracts monitors, dashboards, a normalized **metric-query map** over the configured namespaces (`build_monitors_index(path, namespaces=…)`; ~320 `ec.*` on the real repo; merged into the Datadog adapter's registry via `copilot.merged_metric_queries`, precedence `DATADOG_METRIC_QUERIES` > extracted > live-discovered, then namespace-filtered; **extraction is trusted for aggregation but not for existence** — when discovery returns anything, extracted metrics absent from the live list are dropped, because the `.tf` files reference metrics that no longer emit, and a metric that can't return data must not be selectable as evidence; discovery returning nothing keeps the full extracted set) and a vocabulary **alias map** ("message processing" → its metrics). `service_vocabulary(names)` turns in-scope metric names into guard vocabulary ("ec.quota_manager.x" → "quota manager"), so a namespace makes hundreds of real service names on-topic with no hand-listing. `resolver.py` deterministically selects the top-8 question-relevant metrics per ask (alias/token matching, golden-set fallback); `build_evidence_catalog(metrics=…)` queries only that selection — a large registry must never mean query-everything. The monitors context is injected into **every** reasoning prompt when non-empty (deliberately not keyword-gated). The **resolver works off the source registry (`available`), not the Terraform index** — live discovery alone yields 420 metrics with no Terraform checkout, and `aliases_from_metric_names` supplies vocabulary in that case. **Verified live 2026-08-05 (supersedes an earlier note that EC's tenant is `kube_namespace`):** the tenant tag is **`tenant`** (`conductperf`, `msanity`, …) and `kube_namespace` is the **environment** dimension (`ep-perflab-uat`, `ep-smarsh-staging`); this org has no `env` tag at all → set `DATADOG_TENANT_TAG=tenant` and `DATADOG_ENV_TAG=kube_namespace`. These metrics are **sparse** (36–153 points per 7 days, zero over 4 hours) → `COPILOT_PLATFORM_DEFAULT_WINDOW_DAYS=7`. Tests use fixture Terraform trees in `tmp_path`, never the real checkout. See `docs/MONITORS_INTEGRATION.md`.
- **`app/telemetry/builtin.py` + `data/ec_metric_names.txt`** — the **built-in metric registry**: the 633 metric names read off the live org, committed. Yields **225 queryable signals with no discovery call and nothing in `.env`**, so a discovery failure (a TLS-inspection proxy did exactly this once) can no longer leave the copilot with nothing to query. **This is authority-grade and deliberately NOT under `app/knowledge/`** — it is an observation of what the org emits, not an inference, so it must not inherit the hint-layer contract. `default_query` derives the aggregation from the name shape (`_rate` → `sum:…as_rate()`, `.count`/`_counter` → `sum:…as_count()`, else `avg:`), because `avg:` on a counter answers a question nobody asked. **The `.count` trap:** `ec.centralised_audit.conduct.*.count` are 36 *real* funnel counters, not generated sub-metrics; `is_stat_submetric(name, known)` distinguishes them exactly — Datadog emits `X.count` only alongside base metric `X`, so a suffixed name whose base is **absent** is real. Pass the widest name universe available, never the bounded selection.
- **`app/knowledge/questions.py` + `data/questions.json`** — the **answerable-question catalog**: 36 curated questions, each with an intent, the exact `resolvedQuery`, and an answer shape. `match_question` resolves a user's phrasing onto one deterministically (IDF-weighted overlap + slot bonus, gated by intent family and by recall **on the asked side**); `match_unanswerable` identifies a recognized question whose series this org does not emit. **Hint layer like the rest of `app/knowledge/` — only 17 of 36 entries cite metrics that exist.** **Substitution is the failure mode to design against**: a near-miss entry attaches a confident "these series answer it" block to series answering something else, which is worse than no match — hence the two gates (correct matches score ≥0.68 recall, substitutions ≤0.32; threshold 0.5), pinned by `test_every_catalog_question_matches_itself_or_nothing`. Catalog queries are normalized before use: scope reset to `{*}` and `by {…}` stripped, because the adapter rewrites the first brace block from the Scope and reads `series[0]` only. Wired additively into four seams (resolver `CATALOG_WEIGHT`, engine prompt `RESOLVED QUESTION` / `UNANSWERABLE QUESTION`, adapter registry, guard `recognizer`), each with a spec asserting that omitting it reproduces the prior behaviour byte for byte.
- **`app/knowledge/`** — the **EC NLP layer**: how people actually talk about this platform, mapped onto real telemetry. Five curated JSON files in `data/` (monitor/dashboard dictionary, NLP grammar + 11-stage communication lifecycle, metrics NLP + interpreter spec, worked examples, error catalog), committed and version-controlled; stdlib `json` only, **no new dependency**. `loader.py` is tolerant by contract (missing dir / absent file / invalid JSON / non-object → empty or partial, recorded in `failed`, **never raises**). `vocabulary.py` inverts all five into ~548 `phrase → meaning` entries plus intent/suffix/op-token/stage/monitor-metric tables; it derives a repo's metric segment when the declared `groupName` is a placeholder like `"(not read)"`, and bridges repo-vs-metric plurality (`manual-runs-service` → `manual_run_service`). `text.py` does word-boundary matching with a **closed** inflection set (so "index"/"indexing" match but "count"/"country" cannot) plus contraction expansion. `interpret.py` resolves intent/service/object/percentile/window/stage deterministically — no LLM call. `gaps.py` surfaces the two dangerous shapes the dictionary records: zero-monitor concepts (`kafka.consumer_lag` — 57 dashboard widgets, **0 monitors**) and no-data traps (a monitor wired ahead of its metric reads green forever). **The binding rule is HINT LAYER, NEVER AUTHORITY:** these files may *propose* metrics, but only the live registry decides what exists — parts of them are self-declared "inferred", and 137 of the Terraform repo's 320 metrics are already known dead. A proposed metric absent from `available` is never returned, scored, or citable. Wired **additively** into three seams — `resolver.select_metrics(vocabulary=…)`, the engine prompt (`RESOLVED TERMS` + `COVERAGE GAPS`), and `build_copilot`'s guard vocabulary — each of which behaves byte-for-byte as before when no vocabulary is supplied. **Guard safety:** single-word phrases are admitted only from service/monitor/dashboard kinds; the concept/object lists contribute "message", "record", "status", which as substrings would fast-allow nearly anything.
- **Answer shape (two surfaces, one reasoning pass).** `Investigation.summary` is the **chat headline** — one sentence, ≤25 words, must carry a number. `Investigation.narrative` is the **descriptive read** (3–6 sentences of mechanism) rendered by the Workspace panel and the Incident Summary artifact. Prose belongs in the second, never the first. `Evidence` carries structured `service/stage/has_data/points/unit/baseline/latest/extreme`, so the reply renders from **fields, not re-parsed prose** — it cannot disagree with the telemetry it came from. A **queried-but-empty** metric is kept and flagged (`has_data=False`), because "we looked and found nothing" is a different answer from "we never looked", which matters on this org's sparse metrics. `gaps` and `mapping` are recorded **deterministically** and are never asked of the model, so a missing monitor can't be quietly omitted from a confident reply. Confidence travels through persistence and copy-to-clipboard as a plain `[high]` token and becomes a coloured chip in `renderMarkdown` — so reloaded history is chipped too. All new fields are defaulted; older snapshots still deserialize.
- **`metrics/`** — separate vibe-coding metrics subsystem (not part of the product). `collector.py` (stdlib-only) is run by the **`Stop` hook** in `.claude/settings.json` and appends one record per prompt cycle to `prompts.jsonl`; `analytics.py` is a tolerant loader/aggregator; `dashboard.py` + `static/` serve a dependency-free canvas dashboard.
- **`scripts/`** — safe, human-runnable diagnostics: `check_env.py` (reports which `.env`/config keys are set — never their values — and what `Settings` resolves to) and `datadog_probe.py` (makes read-only calls against a real Datadog org and prints request/response shapes, to tune `app/telemetry/datadog.py` — it discovers metric names first, then targets a **confirmed-live** metric, because an idle metric makes the tag/query steps silently inconclusive). Also `check_testing_log.py`, the pre-commit guard above (stdlib-only, no `app/` imports, so the hook can't break when the venv isn't active).

The **persona system, Workspace sections, and artifact types are registry/config-driven, not hard-coded** (kickoff §8) — they are designed to grow. Keep that seam intact when extending.

## Operating model (non-negotiable — kickoff §2)

The human partner **does not write, edit, or debug code, ever**. Internalize this; it shapes every workflow:

- **Claude owns 100% of technical execution** — code, config, tests, scripts, schemas, mock-data generators, and the run instructions.
- **The human owns approvals and physical actions only**, and only when given exact, copy-pasteable commands: approving plans/designs/dependencies, creating the repo, running commits, running things locally and pasting output back, and account/key setup.
- **Work proceeds through approval gates:** Plan → Design → Roadmap → (human approval) → Implementation, iteration by iteration. Nothing significant proceeds without an explicit "approved."
- **Plan before code, always.** When the charter and a coding instinct conflict (e.g. "just scaffold it and show the user"), the charter wins — ask first.
- **Propose, don't silently decide** anything that adds a dependency, changes architecture, or affects cost/security. Give recommendation + alternatives + trade-off + a default, then wait. No paid service or external dependency may be added without explicit approval.
- **One clear action at a time** when the human must act: numbered, with literal commands and where to type them. Never assume developer conventions (PATH, venv, etc.) are known.
- Label assumptions explicitly so they can be corrected. End each session by stating what got done, what's next, and what's needed to proceed.

## What is being built

An **AI-powered Observability Copilot** — a reasoning layer on top of observability telemetry that turns dashboards into guided, evidence-backed investigations. It is explicitly *not* a chatbot and *not* a dashboard replacement; the dashboard stays the primary source of truth and the Copilot interprets over it. The product lifecycle to embody: **Observe → Understand → Investigate → Explain → Recommend → Execute → Document → Learn.**

Core philosophy that constrains every feature: explain metrics rather than expose them; tell the story rather than show graphs; every conclusion carries supporting evidence; and the AI must always distinguish **Facts vs. Hypotheses vs. Recommendations vs. Unknowns**, with confidence derived from and traceable to evidence — never speculation presented as certainty.

## Architecture (the seams to preserve — kickoff §5, §8)

We build a **coherent working slice, architected for extension**, not the whole product. Establish clean, replaceable seams across four layers:

- **Telemetry / data layer** — synthetic/mock telemetry for now, behind an interface so a real metrics/logs/traces backend can replace it without rewrites. Must support **replaying a known incident** (canonical: a deployment-induced latency incident) so the live demo is reliable, while the AI reasoning over it stays genuine (never hard-coded answers). All event sources (deploys, metric threshold crossings, log spikes, trace anomalies, support signals) normalize into a **common timestamped event model** that merges into one ordered timeline.
- **Reasoning / AI layer** — produces structured reasoning objects, each carrying: the claim, its category (fact/hypothesis/recommendation/unknown), a confidence level, and pointers to supporting/contradicting evidence. Root-cause hypotheses are first-class objects with for/against evidence and required "contradictory evidence" and "missing information" fields; confidence must be revisable and hypotheses retirable as evidence changes.
- **Investigation-state layer — the Investigation Workspace (architectural center of gravity, kickoff §5.9).** A real persisted, versioned investigation-state model — a *living document*, not derived from chat. Each new observation reinforces, contradicts, or refines prior conclusions; historical reasoning stays visible (append-with-history, confidence over time, contradiction tracking). Personas render *from* it, the conversation reads/writes *to* it, artifacts serialize *from* it.
- **Presentation layer** — dashboard + copilot UI coexisting (dashboard alongside an investigation panel, not full-screen chat). Progressive disclosure: headline → summary → evidence → raw telemetry, with "show me the evidence" a first-class, always-available action.

**Extensibility requirement:** the **persona system**, the **Workspace sections**, and the **output-artifact types** must all be registry/config-driven, not hard-coded — they will grow. A persona is a config (which concerns to surface, vocabulary level, detail depth) that changes only the rendering lens, never the underlying facts. Each artifact (Incident Summary, Executive Briefing, Technical Investigation Report, Customer Communication Draft, Post-Incident Report, Runbook Recommendation) is a transform over the same Workspace state; runbook recommendations are gated on a confidence threshold and must always cite evidence. Downstream integrations (incident management, ticketing, comms) are **stubbed adapters behind clean interfaces** for now.

## Demo has two objectives (kickoff §7)

- **Product story (A):** the live narrative — complex dashboard → activate Copilot → health summary → significant changes → operational timeline → likely cause → evidence → persona-adapted explanations → at least one generated artifact, all backed by the living Workspace.
- **Meta story (B), which matters most:** demonstrating that *a non-developer directed AI to design and build a working AI-powered solution rapidly*. The **process is the message** — treat the build journey as a first-class deliverable (this is why `BUILD-LOG.md` and `DECISIONS.md` exist). Optimize for a quick, credible, easy-to-run, easy-to-explain solution over heavyweight engineering. When a choice makes the product marginally fancier but the story slower or harder to explain, prefer the simpler, faster, more explainable path.
